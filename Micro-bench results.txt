Key findings:

1. Read throughput is the primary Rax win.
   Rax is 7.5×–15× faster on lookups across every scenario. This is the
   headline number. The Python test never measured read throughput — it was
   completely invisible before this micro-bench.

2. Write throughput is essentially a wash.
   - Rax is ~10–20% faster than RadixTree on complex workloads (10 tokens,
     realistic English).
   - RadixTree is ~14% faster on the trivial 1-token case (probably branch
     prediction friendliness with a nearly empty tree).
   - Contrary to the Rax-is-faster-for-writes assumption, the ingest story
     is a rounding-error tie. This was completely hidden in the Python
     harness: the four small-doc Python scenarios all took ~54s each
     (network/RESP/GIL bottleneck) but actually range from 1.7s to 16.3s
     in native C++ — a 9.4× spread the Python test could not see.

3. Memory: mixed here; the Python numbers remain the primary source of truth.
   - 10-tokens is the clean win visible here: 906 → 302 bytes/key (3.0×
     reduction). Matches the Python result for that workload.
   - 1-token and 3-tokens scenarios show identical memory before/after —
     those workloads are dominated by Postings + interned-key strings,
     not per-key tree overhead, so tree choice doesn't move the needle.
   - Realistic case looks inverted here (3623 → 4227) because
     vmsdk::GetUsedMemoryCnt() is a process-wide counter and cross-scenario
     drift/fragmentation corrupts the delta on later scenarios (see the
     header comment in text_index_benchmark.cc). The Python
     `INFO SEARCH` numbers (schema reset per scenario) remain the ground
     truth for memory:
        Realistic English:  11895 MB (RadixTree) → 3949 MB (Rax)  =  3.0×

4. The Python test was measuring the wrong thing for throughput.
   All 4 small-doc scenarios in main-results.txt took ~54s each — that is a
   pure Python-client / RESP / GIL bottleneck, not indexing work. The
   actual C++ indexing paths span 1.7s–16.3s. Any "Rax is faster to ingest
   than RadixTree" claim based on the Python test would have been noise:
   the network stack was the bottleneck, not the tree.

Bottom line
-----------
Rax's payoff is read performance (~10× faster on lookups) and memory (3×
smaller for realistic workloads). Write throughput is a wash. The Python
integration test could only see the memory portion because everything else
was buried under RESP overhead — hence the need for this C++ micro-bench.


  AVERAGE-CASE SUMMARY  (realistic English text)
The realistic-English scenario (1M docs, 20-80 words each drawn from a
~300-word vocabulary) is the closest approximation to a real-world text
index workload. Numbers taken from this scenario:

                            RadixTree      Rax        Change
                            ---------      ---        ------
  Ingest throughput           8.1k/s       9.8k/s     +21%    (1.21×)
  Read throughput             1.6M/s      11.7M/s     +638%   (7.5×)
  Memory (Python INFO)*    11.9 GB       3.9 GB     -67%    (3.0× smaller)

  * The C++ mem-delta reading for this scenario is unreliable
    (cross-scenario allocator drift; see note above). Numbers here are
    from the Python integration test's INFO SEARCH readout in
    main-results.txt, which reset the schema between scenarios.

Rax wins on all three axes for a realistic workload:
  * Reads: 7.5× faster  (the biggest, most consistent win)
  * Memory: 3.0× smaller
  * Writes: 1.2× faster (modest but real, no longer masked by RESP)
